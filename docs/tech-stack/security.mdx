Four distinct security mechanisms live under `src/lib/security/`, solving four different problems. It's worth not conflating them - they're often confused because they're all "keys":

| Mechanism        | File                 | Problem it solves                                                                                                                           |
| ---------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Vault encryption | `vault-crypto.ts`    | Store third-party credentials so a member can read them back later                                                                          |
| Vault unlock     | `vault-unlock.ts`    | Prove the person at the keyboard is the account owner before a secret is decrypted, even on a weeks-old session                             |
| Sim access code  | `sim/access-code.ts` | Let the simulation CLI authenticate to this app's API with one short club-wide code, no accounts and nothing stored on the caller's machine |
| Rate limiting    | `rate-limit.ts`      | Slow down abuse of unauthenticated/low-friction endpoints                                                                                   |

## The secret vault

The **Vault** page is a shared credential store to keep track of third-party API keys and service logins (Resend, Tailscale, etc.) in one place instead of a shared password doc. Every approved member can open the page, see what entries exist, and reveal any of them - there are no per-person grants and no per-entry access levels.

An entry is just a name, an optional username, the encrypted secret, and a note. Whether that secret is a password or an API key makes no difference to how it is stored or read back.

What gates a reveal is **presence**, not permission: dashboard sessions last for weeks, so an open tab is no proof of who is sitting in front of it. Reading a secret therefore needs a fresh password check first.

### Encryption at rest - AES-256-GCM

Vault secrets need to be decrypted back to their original value (unlike a password, which only ever needs to be _checked_, never _read_), so they're encrypted, not hashed. `src/lib/security/vault-crypto.ts`:

```ts
const ALGORITHM = "aes-256-gcm";
const KEY_BYTES = 32; // AES-256
const IV_BYTES = 12; // standard GCM nonce length

export function encryptSecret(plaintext: string): string {
    const iv = randomBytes(IV_BYTES);
    const cipher = createCipheriv(ALGORITHM, getVaultKey(), iv);
    const ciphertext = Buffer.concat([cipher.update(plaintext, "utf8"), cipher.final()]);
    const tag = cipher.getAuthTag();
    return `${iv.toString("hex")}.${tag.toString("hex")}.${ciphertext.toString("hex")}`;
}
```

Each encrypted value is stored as one string - `iv.tag.ciphertext`, all hex - so it fits in a single database column. A fresh random IV (nonce) is generated per encryption call, which is required for GCM: reusing an IV with the same key breaks the encryption's confidentiality guarantees. The auth tag is GCM's built-in tamper-detection - `decryptSecret` will throw rather than return corrupted plaintext if the ciphertext was altered.

**Key resolution**, in order:

1. `VAULT_ENCRYPTION_KEY` env var, if set (must be exactly 64 hex characters / 32 bytes - generate with `openssl rand -hex 32`).
2. If unset **and** `NODE_ENV === "production"` - throws immediately. Production is never allowed to silently fall back to a generated key.
3. Otherwise (local dev) - generates a random key on first use and **persists it** to `db/vault.key` (next to the SQLite file, gitignored), so secrets stay decryptable across dev-server restarts. A console warning is printed the first time this happens.

<Callout type="warning" title="Caution">
    Losing `VAULT_ENCRYPTION_KEY` (or `db/vault.key` in dev) makes every existing vault entry
    permanently unrecoverable - there's no way to decrypt without it. Back it up separately from the
    database, and rotate it only if you're prepared to re-enter every stored secret.
</Callout>

### Unlocking the vault - `src/lib/security/vault-unlock.ts`

`POST /api/vault/unlock` takes the member's own dashboard password, verifies it against the stored credential hash through better-auth's own hasher, and mints a signed, HTTP-only `vault_unlock` cookie good for 10 minutes:

```ts
export function createUnlockToken(userId: string, now = Date.now()) {
    const expiresAt = now + UNLOCK_WINDOW_MS;
    const payload = `${userId}.${expiresAt}`;
    return { value: `${payload}.${sign(payload)}`, expiresAt }; // [!code highlight]
}
```

The payload is HMAC-SHA256-signed with `BETTER_AUTH_SECRET` and bound to one user id, so it can't be forged, lengthened, or handed to another account. `DELETE /api/vault/unlock` clears it ("Lock now"), and the UI re-locks itself when the window lapses.

Wrong passwords spend from a 5-per-minute budget keyed by user **and** IP, so the prompt can't be used to brute-force an account password.

### Fetching a secret - the API endpoint

```bash
GET /api/vault/{id}/reveal   # returns { username, secret, expiresAt }
```

It is authenticated by the caller's dashboard session cookie (not a separate API key), and:

- Requires a live `vault_unlock` cookie - without one it returns `403 { error: "Vault is locked", locked: true }`, which is what makes the lock a server-side rule rather than a UI state.
- Independently re-checks `isActive`, because `/api/*` isn't covered by `middleware.ts` (see [Architecture Overview](/architecture/#how-a-page-request-is-authorized-three-layers)).
- Sets `Cache-Control: no-store` so a decrypted secret is never cached by a browser or intermediary.

<Callout type="info" title="No service API keys">
    The dashboard has no issued-API-key system of its own. External callers (the simulation CLI)
    authenticate with the sim access code below; everything else goes through a session cookie.
</Callout>

## Sim access code (`src/lib/sim/access-code.ts`)

Separate from the vault entirely - this authenticates _external scripts_ (the simulation CLI) calling into this app's API, not humans logging into the dashboard. It is one 6-digit code shared by the whole club, held in the single-row `simAccessCode` table:

```ts
export function getAccessCode(now: Date = new Date()): AccessCode {
    const row = db.select().from(simAccessCode).where(eq(simAccessCode.id, ROW_ID)).get();
    if (!row || row.rotatesAt.getTime() <= now.getTime()) {
        return issue(now, null);
    }
    return { code: row.code, rotatesAt: row.rotatesAt };
}
```

Rotation is lazy rather than scheduled: every read checks whether 3am Pacific has passed and issues a new code if so, which means no cron job and no way for a restart to leave a stale code in place. Any dashboard user can also rotate it immediately from the Vault page, recorded in `rotatedBy`.

The code is stored in plaintext on purpose - unlike a hashed API key, a lead has to be able to read it off the screen to share it. What limits the damage is its lifetime (a day at most) and the scope of what it unlocks (CAD exports the club already publishes doc IDs for). Guessing is handled by the rate limiter below: wrong codes spend from a 10-per-hour per-IP budget while correct ones never do.

## Rate limiting (`src/lib/security/rate-limit.ts`)

A simple in-memory [token bucket](https://en.wikipedia.org/wiki/Token_bucket), backed by an `lru-cache` keyed per caller (typically by IP, via `clientIp()`):

```ts
const CAPACITY = 30;
const REFILL_PER_MS = CAPACITY / 60_000; // refills to full over 60s

export function rateLimit(key: string): RateLimitResult {
    // ...refill tokens proportional to elapsed time, then consume one if available
}
```

Each key gets a bucket of 30 tokens that refills continuously back to 30 over a minute; every checked request consumes one token, and requests are rejected (with a computed `retryAfter` in seconds) once the bucket is empty. `clientIp()` reads `x-forwarded-for` (falling back to `cf-connecting-ip`) - both are injected by the Cloudflare Tunnel in front of production, which is what makes per-caller limiting possible despite the app itself only ever seeing traffic from the tunnel.

Being in-memory (an `LRUCache`, not the database), this state resets whenever the process restarts and doesn't share state across multiple server instances - fine for this app's single-instance deployment, but worth knowing if that ever changes.
